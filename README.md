## 一、快速开始

### 环境要求

- **Python 3.9+** 与 **PySide6**（`python -m pip install PySide6`）
- **ADB** —— 从 [platform-tools](https://developer.android.com/tools/releases/platform-tools) 下载，
  放到 `adb/adb.exe`（Windows）或 `adb/adb`（Linux/macOS），或直接加进系统 PATH
- 一台**已 root** 的安卓手机（Magisk / KernelSU / APatch 均可）

> 本仓库不含 ADB 二进制（8 MB 的二进制进 git 历史后无法瘦身），请自行下载。
>
> 💡 **不想装 Python 和 PySide6？** 用发布页的**便携版** —— 自带 Python 运行时与 Qt，
> 解压双击就能用，什么都不用装。

### 运行

```bash
git clone https://github.com/2567922141/android-partition-backup.git
cd android-partition-backup

# 把 platform-tools 里的 adb 放进来（三选一）
#   A. 复制到 adb/adb.exe
#   B. 加进系统 PATH
#   C. 什么都不做 —— 程序会自动从 PATH 找

python -m pip install PySide6   # 只有这一项第三方依赖
python backup_gui_qt.py         # 启动图形界面
```

Linux / macOS 用户可直接用附带的启动脚本（会自动挑一个装了 PySide6 的 Python）：

```bash
./run.sh
```

命令行版（无界面，适合脚本化）：

```bash
python backup_core.py --adb <adb路径> --preset critical --out <输出目录>
python backup_core.py --adb <adb路径> --list        # 只列出设备分区与分级
```

### 手机侧准备

1. 设置 → 关于手机 → 连点「版本号」7 次开启开发者选项
2. 开发者选项 → 打开 **USB 调试**
3. 用数据线连电脑，手机上弹出「允许 USB 调试」→ **勾选「一律允许」并确定**
4. **解锁手机屏幕**（锁屏状态下 adb 常被系统拦截）
5. 确保手机已 root，并在 root 管理器里给 **Shell** 授权

程序会自动识别设备状态，并在界面上提示当前卡在哪一步。

## 二、备份什么 —— 四级分类

程序不看机型，而是**按分区名的语义**自动分级：

| 级别 | 含义 | 典型分区 | 丢了会怎样 |
|---|---|---|---|
| **★ Tier 1 不可再生** | 含设备唯一数据 | `persist` `modemst1/2` `fsg` `nvdata` `efs` `devinfo` `frp` `secdata` | **永久损坏，官方固件也救不回** |
| **Tier 2 root 基准** | 你修补过的系统分区 | `init_boot_a/b` `boot_a/b` `vbmeta*` `dtbo*` | 官方只有未修补版，root 状态丢失 |
| **Tier 3 固件可重建** | 官方刷机包里就有 | `system` `vendor` `abl` `modem` `super` | 重刷官方包即可 |
| **Tier 4 低价值** | 厂商备份槽/日志/对齐 | `bk*` `ALIGN*` `logfs` `oops` `rawdump` | 无意义 |

**预设方案**（界面上一键切换）：

| 预设 | 内容 | 典型体积 |
|---|---|---|
| **关键分区（推荐）** | 只含 Tier 1 | ~80 MB |
| **关键 + root 基准** | Tier 1 + Tier 2（默认）| ~1 GB |
| 全部有价值分区 | Tier 1+2+3 | 数 GB ~ 数十 GB |
| 全部分区 | 所有 | 可达 200 GB+ |

> 📚 **分级规则经过外部核实**：本文的分区名单与 [onfix.cn《手机字库基带使用命令备份指南》](https://onfix.cn/course/4780?bid=1&mid=28642)
> 独立列出的名单逐条一致（高通 `fsg/fsc/modemst1/modemst2`；联发科 `nvram/nvdata/nvcfg/persist/protect1/protect2/seccfg`）。
> 该来源同时印证了「联发科的 by-name 路径与高通不同，需要多路径探测」这一点。

> ⚠️ `userdata`（个人数据，可达数百 GB）、`super`（动态分区容器）、`metadata`（加密元数据）
> **永远不会被预设自动勾选**，需要你手动选中 —— 避免"全选"顺手带上几百 GB。

```
安卓分区备份工具_便携版\
└── Backups\                        ← 程序目录下自动创建
    ├── 我的备份\                    ← 你自定义的名称
    │   ├── .device_info            ← 设备指纹（用于判断"同一台设备"）
    │   ├── README.md               ← 自动生成：设备信息 + 差异对比 + 文件清单
    │   ├── manifest.txt            ← 逐项 SHA256
    │   ├── backup_log.txt          ← 本次完整日志
    │   ├── img\                    ← 分区镜像
    │   └── gpt\                    ← GPT 分区表（头/尾/sgdisk格式/布局文本）
    └── 我的备份_20260918\           ← 同名再次备份 → 自动加日期
```

### 命名与冲突规则

名称由你在界面上**自定义**（留空则用默认名 `Backup`）。同名时按以下顺序消解，**绝不覆盖任何已有备份**：

| 情况 | 结果 |
|---|---|
| 该名称尚未使用 | `我的备份` |
| 已存在，且是**同一台设备** | `我的备份_20260918` ← 追加日期 |
| 已存在，但是**别的设备** | `我的备份_20260918` ← 同样加日期，不把两台机器混一起 |
| 同一天又备了一次 | `我的备份_20260918_153000` ← 再加时分秒 |
| 还是冲突 | `我的备份_20260918_153000_2` ← 再加序号 |

**界面会实时预览最终路径**，并在备份前告诉你为什么是这个名字。

> 🛡️ 自定义名称会经过安全净化（`..\..\Windows` → `____Windows`），
> 确保备份永远落在你指定的根目录之内。

## 四、🛡️ 安全声明

**本工具只做只读导出。**

| 项目 | 说明 |
|---|---|
| 读 / 写 | 对设备分区**只有** `dd if=<分区>` 读取，**全代码不存在任何写设备分区的路径** |
| 设备端写入 | 唯一的写入是 `/sdcard/.apb_tmp` 与 `/data/local/tmp` 下的临时文件，**用完立即删除** |
| 覆盖已有备份 | **不可能** —— 创建目录用 `exist_ok=False`，重名自动改名 |
| 命令注入 | 分区名经过白名单正则 `^[A-Za-z0-9_.\-]{1,64}$` 校验 |
| 路径穿越 | 自定义名称过滤 `/ \ ..` 与 Windows 非法字符 |
| 卡死保护 | 传输停滞 120 秒自动中止（防止 adb 挂住导致无限等待）|
| 取消 | 随时可取消，已完成的分区文件保留 |

**恢复功能不提供** —— 写分区是变砖的唯一途径。参考命令只写进每次备份生成的**备份目录**里的 `README.md`，需要时自行手工执行。

本项目绝对不泄露任何个人信息。

## 五、校验机制

校验的目的不是「多算几遍哈希」，而是**让每一层都能抓住上一层抓不到的失效**。
所以校验点被有意放在数据流的不同位置上：

```
设备闪存 ──①设备端哈希──▶ adb 传输 ──②PC端哈希──▶ 落盘
             闭合传输环              确认落盘正确
```

> 把 sha256 / sha1 / md5 三个并联起来算**不叫多层** —— 它们读的是同一批字节、
> 抓的是同一类错误，任一能抓的另外两个都能抓。**只有位置不同才算一层。**

### ① 设备端哈希（默认开启）⭐

设备自己先算一遍 `sha256sum /dev/block/by-name/<分区>`，与本地收到的字节比对。

这是**唯一能证明「设备上的字节 == 你硬盘上的字节」**的一层。头尾抽样回读、
双读比对、换第二条传输路径 —— 这些能抓的东西它全抓得到，所以有了它就不需要那些。

**代价几乎为零**：UFS 顺序读有 1~2 GB/s，而 adb 传输通常只有 30~150 MB/s ——
对同一个分区，校验耗时只有传输耗时的百分之几。

超过 **1 GiB** 的分区会自动跳过（那已是可再生的 `super`/`userdata`）。

| 分区 | 大小 | 设备端校验 |
|---|---|---|
| `secdata` | 32 KB | ✅ 校验 |
| `frp` | 512 KB | ✅ 校验 |
| `modemst1` / `modemst2` / `fsg` | 8 MB | ✅ 校验 |
| `devinfo` | 16 MB | ✅ 校验 |
| `persist` | 32 MB | ✅ 校验 |
| `recovery_a` / `boot_a` | 100 ~ 192 MB | ✅ 校验 |
| `super` | 9 GB | 跳过 |
| `userdata` | 226 GB | 跳过 |

**所有不可再生分区都在阈值之下**，也就是说最需要保护的那批一定验得到。

关闭方式：GUI 里取消勾选「设备端二次校验」，或命令行加 `--no-verify-device`。

> 如果设备端因为任何原因没算出哈希（没有 `sha256sum`、权限不足…），程序**不会
> 当成失败**，但会在日志里明确写「这一项未做二次校验」，并在完成弹窗里报出
> 未校验的条数 —— 绝不假装验过了。

### ② PC 端哈希 + 精确字节数

### 为什么必须用 `exec-out` 而不是 `shell`？

`adb shell` 会分配 PTY，把二进制流里的 `\n` 转换成 `\r\n`，**静默损坏数据**。

实测数据（32 MB 的 persist 分区）：

| 方式 | 收到字节数 | SHA256 |
|---|---|---|
| `exec-out` | 33554432 | ✅ 与设备完全一致 |
| `shell (PTY)` | **33631171**（多 76739 字节）| ❌ 完全不匹配 |

#### 设备信息栏

读的全是**系统自己的属性**（`getprop` + `uname` + `/proc/meminfo` + `wm size`），一次往返读完，不改动设备上任何东西：

| 字段 | 来源 | 说明 |
|---|---|---|
| 系统 | `ro.build.version.release` / `.sdk` | 如 `Android 16（SDK 36）` |
| 系统版本 | `ro.build.version.incremental` | 如 `OS1.0.1.0.ABCDEF` |
| 芯片 | `ro.soc.model` / `ro.soc.manufacturer` | Android 12+ 的系统权威值 |
| 平台 | `ro.board.platform` | 高通内部代号，如 `kalama` |
| 内核 | `uname -r` | |
| 架构 | `ro.product.cpu.abi` | 如 `arm64-v8a` |
| 内存 | `/proc/meminfo` MemTotal | |
| 屏幕 | `wm size` | 物理分辨率 |
| 槽位 | `ro.boot.slot_suffix` | A/B 设备当前系统槽 |
| 补丁 | `ro.build.version.security_patch` | |
| Root | `su -c id` | 含 SELinux 上下文 |

> 🔍 **芯片型号不猜** —— 优先用 `ro.soc.model`；只有在它缺失时才查一张**很小的**
> 平台代号对照表（`kalama → 骁龙 8 Gen 2`），且一定把原始代号一并显示出来供你核对。
> 查不到就照实显示原始值，取不到的字段一律显示 `—`，不编。
>
> ⚠️ **「系统版本」用的是 `ro.build.version.incremental`，不是 `ro.build.display.id`。**
> 后者在小米/红米上是 **AOSP 构建号**（真机实测为 `BP1A.240101.001`），
> 不是你在「设置 → 关于手机」里看到的那个版本号 —— 一开始就取错了这个，真机验证才发现。
> 同样地，内核以 `uname -r` 为准：有些 ROM 的 `ro.kernel.version` 只有 `5.15`
> 这种两位短值，让它抢先的话界面上就只剩个 `5.15` 了。
>
> 📐 这一排用 `FlowLayout`（自定义流式布局）铺，**窗口窄了自动折行**，不会丢字段
> （真机 1060px 宽时 3 行；760px 时 4 行，实测无越界）。
> 内核/内存/屏幕走的是 `shell` 而不是 `su` —— 这几项普通权限就能读，
> **没 root 的设备也能看到**。

**四条进度条 / ETA 设计要点**：

| 特性 | 说明 |
|---|---|
| **两条进度条** | 上=当前分区，下=总体（含所有已选分区 + GPT + 环境包）|
| **双 ETA** | 当前分区剩余时间 + 整体剩余时间 |
| **速度平滑** | 用指数滑动平均，不是瞬时值 —— 否则数字会乱跳 |
| **窗口标题同步** | 标题栏显示 `备份中 36%`，最小化后看任务栏也能知道进度 |
| **分阶段切换** | 传输时是百分比进度条；SHA256 校验、GPT 读取、tar 打包时自动切成来回滚动条 |
| **日志分级着色** | 紫=阶段标题，绿=成功，红=失败，黄=告警，灰=细节 |

> ⚠️ 着色判定**前缀标记优先于关键词**。像 `[!] 流式失败，回退到设备端暂存模式`
> 这种带"失败"字样的告警（回退后其实成功了），若先做关键词匹配就会被误染成红色。

### 窗口自适应（响应式布局）

界面在**任何窗口尺寸、任何分辨率、任何 DPI 缩放下都不会有元素被裁掉**。

| 机制 | 解决什么 |
|---|---|
| **窗口尺寸按内容与屏幕实测决定** | 不再写死 `1060x820`。启动时量出内容的真实需求，再夹到屏幕可用区内 |
| **可滚动画布兜底** | 窗口比内容小时自动出现滚动条，保证每个控件都够得着 |
| **横排控件自动折行** | 预设方案、批量按钮、选项开关等在窄窗口下折到下一行，而不是被挤出可视区 |
| **分区表格 / 日志双滚动条** | 窗口很窄时横向可拖，列与长日志行不会被切掉 |

> **为什么不能靠 Tk 的 `pack(side="left")`** —— 容器宽度不足时，`pack` 会把**排在后面的控件直接挤出可视区**，既不报错也不提示。表现就是「把窗口调窄之后有些按钮不见了」。
> **为什么也不能用 Tk 的 `grid`** —— `grid` 的**列宽是整个容器共享的**：折行后某个宽控件占了第 0 列，这一列就被撑宽，**其它行也跟着右移**。把列号按行号错开也没用，因为第 1 行仍然要排在第 0 行那些列之后。
> 最终方案：自写流式布局（`FlowFrame` / Qt 版的 `FlowLayout`，自己算坐标折行）+ 滚动兜底（`ScrollHost` / Qt 版的 `QScrollArea`）。
>
> 📌 **v2.0.0 之后**：Qt 的布局系统本身就比 Tk 稳健得多，`QScrollArea` 也是原生控件而非手写 Canvas 方案。
> 上面这段 Tk 时代的踩坑记录保留下来，是因为它解释了**为什么这个项目一定要自己管折行**，而不是交给布局管理器。

### ADB 服务开关

界面上有一行 **`ADB 服务: ● 运行中  [停止]  退出本程序时会自动停止 ADB 服务`** ——
**就在最顶部的「① 设备状态」里**，和「刷新设备 / 检查 Root」挨着，随手就能启停。

| 控件 | 作用 |
|---|---|
| 状态文字 | 实时显示 adb 服务端在不在跑（每 2.5 秒查一次，毫秒级端口探测） |
| `[启动]` / `[停止]` | 手动启停 adb 服务端 |
| 退出时自动停止 | **无条件执行**，不需要设置 —— 关窗时自动 `adb kill-server` |

**为什么要给这个开关** —— adb 服务端（监听 `5037`）是**多个工具共用**的常驻进程（Android Studio、scrcpy 用的是同一个）。所以本程序运行期间不会擅自杀它（只在你显式点「停止」时停），但**退出时一定会停掉**，不留残留进程。

> ⚠️ **点「停止」会同时暂停设备检测** —— 否则轮询线程下一轮的 `adb devices` 会立刻把服务端又拉起来，表现就是「点了停止没反应」。恢复点「启动」即可。

#### 关窗时会做四件事

```
① poll_stop.set()         让后台线程别再发起新的 adb 调用
② kill_live_children()    杀掉还在跑的 adb 子进程
③ adb kill-server         停掉服务端（无条件，且必须在 ② 之后）
④ 等后台线程退出（≤0.6s）  然后 destroy()
```

> ❗ **为什么必须自己清** —— adb 子进程是**独立进程**，Python 退出不会顺带把它们带走。关窗时若正有一次 adb 调用在飞（设备轮询、读分区表、或一次正在进行的备份），那个 `adb.exe` 就会变成孤儿留在任务管理器里。
> 实测（Windows / Python 3.14）：`Popen(["adb","wait-for-device"])` 之后直接让解释器退出，该 adb 进程**依然存活**。
> 实现上 `backup_core.py` 有一个子进程登记表，7 处 `subprocess.run` 全部改走 `_run()`（它会登记 PID），2 处 `Popen` 补了登记，另加 `atexit` 兜底 —— 无论从哪条路径退出都不会留孤儿。

### 备份完成后打包为压缩包（v2.1.0 新增）

界面上勾选 **`☑ 备份完成后打包为压缩包`**（默认**不勾**），或命令行加 `--archive`。

备份完成后会**额外**产出一个 zip —— **原始文件夹原样保留**，压缩包是**同级的一个文件**：

```
Backups\
└── Redmi K70\                 ← 原始备份目录，一个字节都不动
    ├── img\
    ├── gpt\
    ├── manifest.txt
    └── README.md              ← 恢复要点就在这份里
Backups\
└── Redmi K70.zip              ← 额外产出的压缩包
```

| 项目 | 说明 |
|---|---|
| 格式 | **zip**（标准库 `zipfile` + `ZIP_DEFLATED`），**零第三方依赖、零外部进程** |
| 进度 | 走与备份相同的进度事件（`phase="archive"`），有真实的字节进度与速度 |
| 失败处理 | **打包失败不算备份失败** —— 数据本身是好的，只在日志里告警 |
| 取消 | 打包期间可以取消，半成品会被删掉，源目录不受影响 |

**实测压缩效果**（真实备份，971.5 MB）：

| 输入 | 输出 | 压缩率 | 耗时 |
|---|---|---|---|
| 971.5 MB | **138.7 MB** | 省 **85.7%** | **5.2 秒** |

> 💡 为什么压得这么狠 —— 分区镜像里**大片都是零填充**（未使用的块），deflate 压零几乎不费力。
> 真正难压的只有 `data_adb.tar.gz`（本来就是压缩过的），那一块谁都压不动。

**为什么不做 7z / rar**：

- **rar** —— WinRAR 的 `Rar.exe` 许可证**明确禁止随第三方软件分发**；而 7-Zip **只能解压 rar、不能创建**。所以任何开源工具都无法内置 rar 压缩，这是法律问题不是技术问题。
- **7z** —— 实测同一份数据：7z -mx=9 压到 30.27 MB（省 88.7%，15 秒），zip 压到 38.40 MB（省 85.7%，**2 秒**）。**只多省 3 个百分点，却慢 7.5 倍**，还要用户机器上恰好有 `7z.exe`、找不到就得降级。不值。

> ⚠️ **刻意不用 `ZIP_LZMA`** —— 它体积确实更小（接近 7z），但 **Windows 资源管理器打不开**，等于把「双击即开」这个唯一的价值丢掉了。

> 📌 **一个容易漏掉的细节** —— `manifest.txt` / `README.md` / `backup_log.txt` 是备份**结束之后**才写的（内容依赖备份结果），而打包发生在备份过程**内部**。如果不补这一步，解压出来的备份会**缺掉校验清单和恢复说明**。实现上用 zip 的**追加模式**把这三个文件补进去：只重写中央目录、**不重压任何已有条目**，哪怕包有 971 MB 也是毫秒级。

> 📦 模块划分：打包逻辑在 [`archive_pack.py`](archive_pack.py)，与备份引擎完全解耦。

### 备份进行中：危险操作会被拦下（v2.1.0 新增）

备份跑起来之后，会干扰这次任务的操作**不会被禁用**，而是**保持可点、点了弹窗说明原因**：

> 备份正在进行，暂时不能<动作>。请等它跑完，或先点「✕ 取消」。

被拦下的动作：**刷新设备 / 检查 Root / 启停 ADB 服务 / 更改输出位置（含「恢复默认」）/ 修改预设方案 / 修改表格勾选**。

**为什么是弹窗，而不是把按钮灰掉** —— 灰掉的按钮点不动、也不解释，用户只会以为程序卡死了；
弹窗能直接告诉他「现在为什么不行、该怎么办」。代价是每个入口都得自己拦一次。

其中**预设方案**与**表格勾选**除弹窗外还会**视觉回滚**（单选按钮 / 勾选框退回操作前的状态）——
它们的控件状态在回调触发**之前**就已经变了，只弹窗不退回的话，界面会显示成「已换成 B 方案」，
而实际用的仍是开始那一刻快照下来的 `self.checked`。

备份期间灰掉的只有「开始备份」和「打开输出目录」（前者再点一次没有意义），
**「✕ 取消」全程可用** —— 这是刻意的：唯一能中断任务的操作；状态栏显示
`备份进行中 —— 相关设置已锁定（点击会提示原因）`。

**刻意不拦的三类**（拦了反而更糟）：

- **过滤框 / 隐藏低价值分区勾选框** —— 只改变表格里**可见的行**，不影响备份内容（真正决定内容的是开始时快照的 `self.checked`），而且绑在输入事件上，拦就得「打一个字弹一次窗」。
- **输出路径输入框 / 备份名称输入框** —— 这些值在点「开始备份」的瞬间就被快照进引擎了，备份期间再改**不影响本次任务**。
- **五个选项勾选框**（备份 GPT / 环境包 / 设备端二次校验 / 失败回退 / 打包为压缩包）—— 同上，都在开始那一刻被读走。

> ⚠️ 副作用：这些输入框保持可编辑，所以跑完之后界面显示的值**可能和本次实际用的不一致**。
> 改备份名称时，若路径预览算出的目录 ≠ 本次真正在写的目录，预览行会补一句
> `⚠️ 本次备份仍在写入：<目录>`。

## 八、技术架构（给未来的维护者）

```
backup_gui_qt.py       图形界面（PySide6 / Qt6），只负责显示与交互，**v2.0.0 起的默认界面**
  ├─ 设备轮询线程       每 1.5 秒查一次 adb devices
  ├─ 消息队列 queue     工作线程 → 主线程的唯一通道
  └─ QTimer 消息泵      主线程每 80ms 取一次队列并刷新界面

backup_gui.py          【旧版】图形界面（Tkinter），1.x 时代的实现，保留作回退
  └─ 与 Qt 版功能对齐，但缩放大尺寸窗口时明显卡顿（架构原因，见下）

backup_core.py         核心引擎（无 GUI 依赖，可 CLI 独立运行）
  ├─ Adb                adb.exe 封装 + 能力探测
  ├─ BackupEngine       备份流程编排
  ├─ GPT 解析器         纯 Python 解析 GPT，不依赖设备端的 sgdisk
  └─ 目录命名/冲突消解   sanitize_folder_name / resolve_backup_dir

partition_profiles.py  平台特征 + 分区四级分类规则（纯数据）
```

### 四条不可违背的设计约束

1. **绝不从工作线程碰 GUI 对象**
   所有 `QLineEdit.text()` / `QCheckBox.isChecked()` 之类的调用必须在主线程完成后再传给工作线程 ——
   否则 Qt 会直接崩（`QObject: Cannot create children for a parent in a different thread`）或随机段错误。
   Qt 在这点上比 Tkinter 更严格：**跨越线程边界只能传数据，不能传控件**。

2. **为什么 v2.0.0 要从 Tkinter 换到 Qt**
   Tk 在 Windows 上给**每个控件建一个真实 HWND**。本程序 114 个控件、嵌套 8 层，
   每次改窗口大小 Windows 都要重新调整并重绘它们 —— 实测 **69 ms/次**，拖拽时事件队列永远追不上。
   试过 8 种 Tk 侧优化（扁平化、冻结重排、摘掉滚动条、把内容移出 Canvas……）**全部无效**，
   因为这不是代码写得不好，是 Tk 的架构决定的。
   Qt 的控件不占独立 HWND，缩放是重绘而非窗口重建 —— 实测 **13.7 ms/次，快 4~5 倍**。

3. **必须剥离 A/B 槽位后缀再匹配规则**
   规则表按无槽位名写（`abl`），设备上实际叫 `abl_a`。
   不剥后缀会导致大量分区"未分类"。见 `classify()`。

4. **GPT 偏移必须在 Python 里算**
   shell 的 `[ ]` 比较对 253 GB 这种数值会 **32 位溢出**成负数，
   导致尾部 GPT 被静默跳过。Python 原生 64 位，没有这个问题。

### 如何支持新平台

在 `partition_profiles.py` 的 `PLATFORMS` 里加一条平台特征，
再往 `TIER1_RULES` 等规则表里补 `(fnmatch 模式, 说明)` 即可，**无需改动任何其他代码**。

### 同类项目（调研时发现）

调研找到 **8 个相关项目**，全部浏览过。结论是：现存方案**要么是设备端 CLI、要么是 PC 端命令行**，没有一个提供「PC 端 GUI + 分区多选 + 一键备份 + 自动校验」。
